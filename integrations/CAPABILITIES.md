# 能力清单与组合 —— agent 的地图

这份文档回答两件 `harness` 命令回答不了的事:**能力之间怎么衔接**,以及**不是流程的那些
能力在哪**。至于「有哪些能力、各自什么时候用」——**不要读这里,问引擎**:

```bash
harness abilities
```

每个能力的 `when:` 一行写在它自己的 spec 里,所以那份输出永远与实际一致。
**一份手写的「哪个能力干什么」清单在加进第七个能力的那一刻就过期了**,而一张悄悄
过期的路由表会把工作送进错误的生命周期——比没有表更糟。所以这里不复制它。

## 判断顺序

```
用户的诉求
│
├─ 要改代码 / 要提交 / 要发评审 ─────────────→ shipcheck-asis
├─ 要出一份方案（还没开始做）───────────────→ plan
├─ 手上有方案要推成任务 ────────────────────→ push
├─ 要看**别人的**评审 ──────────────────────→ cr-reviewer
├─ 要把**已做完的**评审归纳成任务 ──────────→ cr-to-task
└─ 都不是（查东西 / 定时任务 / 问知识库）───→ 下面「非流程能力」
```

两组最容易混,而混了的代价不对称:

| 容易混的 | 区别 | 混了会怎样 |
|---|---|---|
| `plan` vs `cr-to-task` | plan 是**做之前**出计划;cr-to-task 是**做之后**补记录 | 用 cr-to-task 去规划未做的事 = 为不存在的工作建单 |
| `cr-reviewer` vs `shipcheck-asis` | 前者评审**别人的**改动,后者交付**自己的** | 用 cr-reviewer 走自己的改动 = 完全没有交付保证 |
| `push` vs `cr-to-task` | push 是 1 份方案→1 条任务;cr-to-task 是 N 条评审→M 条任务 | 用 push 逐条建单 = 得到评审列表的副本 |

## 能力怎么串起来

一条完整的交付链跨**三个能力、三个 run**,由一份方案文档串着:

```
plan            → 产出方案文档（status: pending）
  ↓ 方案文档
push            → 建任务，方案状态 → pushed
  ↓ 任务 + 方案文档
shipcheck-asis  → 执行交付（改码 / 验证 / 提交 / 评审）
  ↓
push（收尾）    → 关任务，方案状态 → done
```

⚠️ **引擎目前不强制这条链。** 三个 run 各自独立,没有任何机制要求 `push` 之前有过
`plan`、或 `shipcheck-asis` 之前有过 `push`。跨 run 的交棒是已知缺口,不是已实现的保证 ——
**不要以为走完一个就自动满足了下一个的前提**。

`cr-reviewer` 与 `cr-to-task` 不在这条链上,各自独立。

## 每条链都要开自己的 run

一个 run 对应一个能力的一次执行。走完 `plan` 不会让 `push` 的 run 自动存在 ——
到了 push 阶段要为它单独 `harness open push --scope <...>`。

各能力的 `scope` 维度不同(代码库 / 方案标识 / 工作区 / 评审 / 迭代),`harness abilities`
会打印。**scope 传错的后果是安静的**:守卫按 scope 找 open run,scope 不匹配就等于没有
守卫,而那和「没什么要守护」长得一样。

## 有一条链的执行不在这里：设计（ux）

`push` 和 `plan` 都有一个 **ux 变体**，而它**只负责派单**。设计流程本身的执行方是**另一个
agent**（`ux-agent`，跑 `~/.kiro/skills/ux/`），不是你。

具体分工，不要弄反：

| 谁 | 做什么 | 在哪 |
|---|---|---|
| 你（本引擎） | 出一份 ux 口味的方案、推成任务、以及后来的收尾契约 | `plan` 的 `G05ux`/`W01ux`、`push` 的 `V01ux`/`C02ux`/`Z01ux` |
| `ux-agent` | U0→U7 的设计流程本身（需求 / IA / userflow / wireframe / 设计系统 / 高保真 / 交棒） | 它自己的 skill 与状态机 |

所以：**推完一份 ux 方案之后不要接着自己做设计。** 那条任务会被 `ux-agent` 领走。
同理，任务描述里带 `🎨 UX-Revision Required` 标记的活是给它的，不是给你的。

**为什么这里没有一个 `ux` ability——这是记录在案的设计决定，不是没填的空缺。** ux 的
`SKILL.md` 正文写着它「只做确定性 resolve/query/record，**不做** transition 强制 / 打分」，
并明确说那套重机械「ux 不要」；它也有自己完整的并行状态机与 hook 注册表。把它拉进来不是
消除重复，是**给另一个 agent 换一个它明确拒绝过的引擎**。

如果哪天这个判断变了，正确的做法是先决定「上报归谁」——两边现在各有一套 fleet 上报，
同时报会在协调方那里产生重复事件。

## 非流程能力

下面这些**不是** ability,因为它们没有步骤、没有门、没有完成判据 —— 把它们做成 flow.yaml
只会得到一个「一个 attest 步 + 零 gate」的空壳,而那正是引擎在别处会 exit 2 拒绝的形状。
它们是工具绑定,直接用即可。

### 定时任务

一个本地调度器,通过 `scheduler_*` MCP 工具管理按 cron 运行的 agent 提示。

- 首次使用要跑一次它的 setup 脚本(路径见该 skill 目录)。
- 任务定义在它自己的 `data/tasks.yaml`;**完整 schema / cron 语法 / 输出变量**在
  `references/task-authoring-guide.md` —— 需要写任务时再读那份,不要预载。
- 面板:`open http://127.0.0.1:19748`
- 三个坑:任务只在 kiro-cli 会话活着时运行;认证令牌会过期(任务开始失败先重新认证);
  MCP server 没起来就重跑 setup 或重启 kiro-cli。

### 常驻经验：手上那份是快照，库才是权威

`hot-set.md` 作为资源常驻在你的上下文里，所以那 15 条经验的**正文你已经有了**，不必再去查一遍
才能用它们。

但**它是快照，不是权威源**。那个文件由 `memory.py promote` 生成并进了版本控制；真正的状态在
一个**机器本地、且刻意不进版本控制**的库里（它累积的是本机的使用信号）。所以两者会漂移——
在一台库被重建过的机器上，文件可能比库旧。

因此交付流程开头那一步要求的**不是**「读那个文件」，而是**问活库**，并且把答案记成一个
可被反驳的声称（`loaded` / `empty` / `unavailable`，各由一个派生事实守着）。**冲突时库赢。**

一句实用的话：**正文从手上这份读，条数与 id 从库里取。** 别把手上这份的条数当成已加载的条数——
「查了确实是空」与「压根没查到」在下游长得一样，而那正是那三路核对要分开的两件事。

### 知识库

查询走 `shared-kb` 的路由:先读它的 `SKILL.md` 决定该问哪个子库,再查。
`L0-meta/routing-rules.md` 是路由规则,`L2-hot/hot-set.md` 是热点集合 —— 两者按需读。

配置里挂了若干 knowledgeBase 索引(服务知识 / skills 包 / 后端 / 设计规范 / 统一 MCP /
marketplace 规范),语义检索直接可用,不需要读文件。

### 代码图谱

跨领域关系与影响面分析:`graphify query` / `path` / `explain`。
包级 AST 图(导入/调用关系)的路径见 `graph/SKILL.md`。

**先问图谱再 grep**:一个作用域内的子图通常比全仓搜索小得多,也更能回答「改这个会牵连谁」。

## 一条给自己的提醒

这份文档里凡是能被派生的,都不该写在这里。现在留下的三类是真的派生不出来的:
**能力之间的衔接关系**、**容易混的那几对及其代价**、**不是流程的那些能力**。

如果哪天发现自己在这里维护一张「能力→用途」的表,那说明 `when:` 字段没写好 ——
去修 spec,不要在这里补。
