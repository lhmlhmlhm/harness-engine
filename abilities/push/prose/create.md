# 创建阶段（Create）

这个阶段把已经选定、已经验证过的方案，**变成任务系统里的一条真任务**。它由一个共享外壳
（确认 → 建单 → 迁移方案状态）和一段变体专属的组装（代码类 / 设计类各写各的任务描述）拼成。
它是这条流程里第一个产生**外部副作用**的地方 —— 一旦建单，任务系统里就多了一条别人会看、
会认领、会据以开工的记录，删掉它比不建它代价高。所以核心不是"快点把单建出来"，而是
"建之前有人真的点过头、建出来的描述不会把执行方带错方向"。

## Step: C01 展示方案摘要并等人确认

> - **输入**：P04 之后的方案（依赖、executor、待确认事项都已 lint 通过）
> - **输出**：一条被如实记录的推送确认决定
> - **失败时**：被守卫拦住时不要动守卫、不要伪造门 —— 没人真的看过就没有这条门
> - **完成标准**：确认门已记录

这是整个阶段唯一的**人工确认门**，也是它必须存在的原因：建单是外部动作，flow 里把
「创建任务」这个动作直接挂在了这道门上（`task_create → C01`）—— 也就是说，**在这道门被
如实记录之前，任何工具都不该替你去建单**。门不是走形式，它是那次外部写入的授权凭据。

做法是两轮，不能压成一轮：

🚦 **这一轮**把要推的东西摊开 —— 走哪个变体、任务描述的要点、落到哪个任务系统 —— 然后
**结束这一轮**，等人真的回话。

⚠️ **下一轮**才记录决定。不要在同一轮里自己把门记成通过：背书机制会检查「上一次门之后有
没有新的人类发言」，你在没有新回复时就记录，会被识别成**伪造门**并拒绝。这不是多此一举 ——
这一步的**全部价值**就是"有人真的看过再点头"，自问自答等于把这个价值抽空，只留一条假记录。

⚠️ 记录时写**人的原话**，不要写你的转述。转述会悄悄改语义：把「可以，但先把 X 去掉」压成
「可以」，一个带条件的放行就变成了无条件放行，而那个条件恰恰是人加上去的。

（若配置显式预授权了自动确认，可免去等待、记一条 auto 决定 —— 但那需要对应授权开关为真，
否则记录同样被拒。默认永远走"停下来等人"。）

## Step: C02sc 代码类描述组装（marker + DoD + 各段）

> - **输入**：C01 已确认的方案
> - **输出**：一段代码类任务描述 —— 含代码类 marker、验收标准块、工作区/交付方式/评审相关各段
> - **失败时**：某段拿不到确定信息就停下问，不要用占位符糊上去建单
> - **完成标准**：描述、marker、验收块三者都已分别记录

**这一步只在代码类变体下存在**，它和设计类的 C02ux 是一对**互斥形态**，不是重复：同一个
"组装任务描述"的位置，代码任务要写的是工作区、交付方式、评审相关的段落，并打上一个**代码类
marker**，让执行方知道"这是要写代码、要提交、要走评审的任务"。设计类那套字段在这里没有意义，
所以由平行的 C02ux 负责，本步在设计类流程里根本不存在。

完成判据要的是**三样各自的证据**：描述、marker、验收块。最典型的做错方式是**只落了"描述"
一样**，以为把 marker 和验收标准都写进那段描述文字里就够了 —— 但判据分别检查这三种证据，
把它们揉成一坨自然文本会让 marker / 验收块两项**查无实据**，判据不过。要把三者当三件独立
产物分别记录，而不是一段富文本。

## Step: C02ux 设计类描述组装（marker + DoD + 各段）

> - **输入**：C01 已确认的方案
> - **输出**：一段设计类任务描述 —— 含设计类 marker、目标项目/参考输入/受影响产物/修订类型、验收标准块
> - **失败时**：目标项目或参考输入信息缺失就停下补，不要凭空编
> - **完成标准**：描述、marker、验收块三者都已分别记录

**这一步只在设计类变体下存在**，是 C02sc 的镜像形态。设计任务描述的字段不同：目标设计
项目、参考输入、受影响产物、修订类型 —— 没有"提交"和"评审合入"这层含义，那层由代码类的
C02sc 负责。读者看到 C02sc / C02ux 并排会以为重复，其实是两个互斥分支，一次流程只会走其一。

⚠️ **最关键、也最容易犯的错：给设计任务注入了代码类 marker。** 直接把 C02sc 的模板抄过来
改字段，很容易连它的代码类 marker 一起带过来。后果是实打实的 —— 执行方是靠 marker 判断
"这是什么任务"的，一条设计任务上出现代码类 marker，会让它在设计任务上**误激活整套代码
生命周期**（去构建、去提交、去发评审），而这条任务根本没有代码要提交。设计类 marker 与
代码类 marker 互斥，本步只打设计类的那一个。

## Step: C03 创建任务

> - **输入**：C01（确认门）+ 本变体的描述组装步（C02sc 或 C02ux）
> - **输出**：任务系统里的一条任务（含 id）
> - **失败时**：建单接口报错就停下回报，不要重复建出多条
> - **完成标准**：任务 id 已记录，且本变体的描述组装步已关闭

这是共享外壳的一步：无论哪个变体，最终都从这里把单建出来。但它有一个约束需要讲清楚 ——
**建单必须在"本变体的描述已经组装好"之后**，否则会建出一条没有 marker、没有验收块的空壳单。

这个约束**没有**写成一条 deps 边，而是写进了完成判据里的 `all_of.any_of` 组
（`任务 id 已记录` **且** `C02sc、C02ux 至少关闭其一`）。原因是引擎的硬规则：**共享步不能
依赖只在某个变体里才存在的步** —— 如果给 C03 加 `deps: [C02sc]`，那么在设计类流程里
C02sc 根本不存在，加载期就会因"依赖了不存在的步"而拒绝整个 ability。用 `any_of` 表达
"这两个组装步，走到哪个变体就关哪个、关掉其一即可"，正是这个原语的用途：它让共享步在
两个变体下都成立，同时仍然把"描述必须先组装完"这条约束钉死。

最典型的做错方式是**只盯着 task_id**：接口返回了 id 就宣布这步完成，而没意识到判据还要求
本变体的组装步已关闭。若组装步没关，即便 id 有了，这步也不算完 —— 该回头把 C02sc / C02ux
真正落完，而不是想办法绕过判据。

## Step: C04 方案文档状态迁移（pending → pushed）

> - **输入**：C03 建单的结果（任务 id）
> - **输出**：方案文档的状态与所在目录，随推送结果更新
> - **失败时**：建单其实没成功就不要迁移状态 —— 状态要跟真实结果走，不跟意图走
> - **完成标准**：状态为 pushed

建单成功后，把方案文档从"待推送"迁到"已推送"，并让它所在的目录跟着状态走。这一步是让
方案区的状态和任务系统的现实保持一致 —— 下次再看方案区，一眼就知道哪些已经推出去了。

最典型的做错方式是**按意图迁移、而不是按结果迁移**：C03 其实报了错、单没建成，却因为
"流程走到这了"就把状态标成 pushed。那会留下一条"标着已推送、实际没有对应任务"的假状态，
比不迁移更难排查。状态必须以 C03 的真实产出（拿到了 id）为前提；没拿到就停在原状态。
