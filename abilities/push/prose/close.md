# 收尾阶段（Close）

这个阶段回答一个问题：**这条任务真的完成了吗？** 完成的判定是变体专属的 —— 代码任务看的是
"评审合入了没、单能不能关"，设计任务看的是"设计流程自己的阶段是不是都走完、交棒产物在不在"，
两者是不同维度，不能互相套用。判定之后才是共享的收尾（关单或明确保持打开、方案文档归档）。
整阶段的步骤都是 optional 的：不是每次推送都要一路盯到合入，但**一旦做判定，就必须如实记录
判定结果，非完成态不得关单**。

## Step: Z01sc 代码类完成判定（评审合入 + 任务可关）

> - **输入**：C04 之后这条代码任务的现状
> - **输出**：这条代码任务是否真的完成的判定（complete / cr_not_merged / still_running）
> - **失败时**：评审未合入 → 告警并保持跟踪，不要替它宣布完成
> - **完成标准**：判定已记录；非 complete 时不得关单

**这一步只在代码类变体下存在**，因为只有代码任务才有"评审合入"这个维度。判定要老实反映现实：
评审已合入才是 `complete`；还没合入是 `cr_not_merged`；评审/验证还在跑是 `still_running`。
这三个都是**合法的记录值** —— 记一条"还没合入"不是失败，装作已完成才是。

最典型的做错方式是**乐观终态**：看到评审开着、检查还在转，就当它"应该会过"而记成 complete。
"还在跑"不是"跑过了"，"已提交待评审"不是"已合入"。把中间态当终态，会让后面的关单在一条
其实没落地的改动上进行。非 complete 时的正确姿态是：记下真实判定、告警、保持跟踪，把关单
这个动作留到真的合入之后。

## Step: Z01ux 设计类完成判定（阶段全 done + 交棒产物存在）

> - **输入**：C04 之后设计流程自己的状态
> - **输出**：这条设计任务是否真的完成的判定（complete / phases_pending）
> - **失败时**：还有阶段没走完 → 记 phases_pending，不要替它宣布完成
> - **完成标准**：判定已记录；phases_pending 时不得关单

**这一步只在设计类变体下存在**，是 Z01sc 的镜像。关键区别：设计任务**不查评审合入** ——
它根本没有"提交—评审—合入"这条链路。它读的是**设计流程自己的状态**：所有设计阶段是否都到
`done`、交棒产物是否已存在。两者都满足才是 `complete`，否则是 `phases_pending`。

最典型的做错方式是**把代码类的判定套过来**：去找一个"评审合入"信号来判断设计任务完成没有 ——
但那个信号在设计任务上不存在，硬找只会找到空值或误判。设计完成的唯一依据是它自己的阶段状态
和交棒产物。还有阶段没到 done 就记 `phases_pending`，并且此时**不得关单** —— 交棒产物没齐
就关单，等于把一份没做完的设计标成了已交付。

## Step: Z02 收尾（任务关闭 + 方案文档归档）

> - **输入**：Z01sc / Z01ux 的完成判定
> - **输出**：任务状态（关闭 / 保持打开）与方案文档归位的处置结果
> - **失败时**：关单接口报错就如实记 kept_open 并说明，不要假装关成功
> - **完成标准**：任务状态与方案文档状态两者的处置都已记录

这是共享收尾：根据前一步的判定，要么把单关掉（`closed`），要么**明确地保持打开**
（`kept_open`）；同时把方案文档归位 —— 已完成的归档为 `done`，未完成的保持 `pushed`。

最典型的做错方式是**只处理"成功关单"这一种情况**：以为收尾就等于关单，于是判定不是 complete
时就什么都不记、直接略过这一步。但判据要的是**两者的处置都被记录** —— **「保持打开」本身就是
一种必须被记下来的处置**，不是"没做"。一条该开着的单被静默略过，和一条忘了处理的单，在事后
看起来一模一样；显式记一条 `kept_open` 才能把"我看过、决定让它开着"和"我漏了"区分开。方案
文档同理：完成就归档 done，没完成就如实停在 pushed，两者都要落。
