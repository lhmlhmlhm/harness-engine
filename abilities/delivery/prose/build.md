# 交付：实现与验证

本文件是 `delivery` 能力 build 阶段的**操作契约**。每个 step 一节，`harness show` 按
标题锚点取出对应那一节。

判断性的东西不写在这里 —— 那些进 `topics/`，只在踩到时才读。这里只写「怎么做、
做完的标准是什么、失败了怎么办」。

## Step: K01 实现

> - **输入**：`C01` 产出的改动清单（path + operation + anchor）
> - **输出**：符合清单的改动 + 一条 `diff` 证据
> - **失败时**：清单里的锚点对不上 → 停下说明，不要凭猜测改别处
> - **完成标准**：`harness evidence --kind diff` 已记录

按清单逐项实现。偏离清单是允许的，但**先说明再改**——清单是上一步和人对齐过的东西，
静默偏离等于把对齐作废。

三条硬约束：

1. **锚点必须实测命中。** 清单里写「在 `foo.py` 的 `def bar` 后插入」，就先 grep 出
   `def bar` 的行号。对不上就是现实与预期不符，属于要上报的情况，不是自己找个相似位置糊上去。
2. **改动范围不超出清单。** 顺手清理无关代码会让影响面复核（`D01`）失去意义——
   复核的是清单，不是你实际改了什么。
3. **不要用 heredoc 写文件。** 用文件写入工具。原因见 topic `heredoc-hangs`，
   那不是风格偏好，是会挂死会话的。

## Step: K02 验证（含变异验证）

> - **输入**：`C02` 的测试基线 + `K01` 的改动
> - **输出**：一条 `test_result` 证据，值里必须含 `pass`
> - **失败时**：既存绿变红 → 是你改坏了，修；本来就红 → 对照基线说明，不算回归
> - **完成标准**：completion predicate 要求证据值匹配 `pass`

跑测试，**与 `C02` 的基线逐条对比**。只允许两种变化：新增绿、既存红变绿。
「既存绿变红」一律是回归，不接受「大概不相关」。

### 变异验证是必须的，不是可选的

新写的测试必须做一次变异验证：**把修复去掉，确认测试真的变红**。

```
1. 备份被修的文件
2. 把修复改回去（或用 sed 定向破坏那一行）
3. 跑测试 → 必须红
4. 还原，再跑 → 必须绿
5. diff 确认还原干净
```

**绿色本身不证明测试有效。** 一个断言写错了对象、或者根本没执行到的测试，永远是绿的。
只有「去掉修复它会红」能证明它在守东西。

两个已知会让变异验证失效的坑，见 topic `mutation-verification-traps`。
