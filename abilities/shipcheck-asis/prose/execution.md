# 执行阶段（Execution）

这个阶段把已通过验证的改动**真正落地**：生成提交信息与评审说明、请人做最后确认、提交代码、
推送到代码评审系统。它是整条流程里**不可逆动作最集中**的地方 —— 一旦提交、推送，就会占用
别人的时间、在外部系统里留下新记录，回退代价远高于前面阶段。所以核心不是"做得快"，而是
"做之前让人看清、做之后如实记录"。做完的标准：改动已提交（有提交哈希），评审已创建，且提交
前的人工确认门已被如实记录 —— 任何一环靠猜、靠自我说服跳过，都算没做完。

## Step: E01 生成提交信息

> - **输入**：本次方案文档 + 代码 diff
> - **输出**：一条结构化提交信息（标题行 + 正文）
> - **失败时**：diff 或方案读不到 → 停下来说，不要凭空编一条信息
> - **完成标准**：标题行符合约定格式，正文说清「改了什么、为什么」

按约定式提交的格式写：`类型(范围): 一句话主题`，再跟一段正文。默认用**英文**书写 ——
全 ASCII 能天然免疫某些环境下的字符集转码问题（非英文字符被转成 `?` 是真出过事故的）。
方案文档里的中文上下文仍是事实源，只是提交信息用英文**复述**同一件事。若明确要求中文，
再切中文，但要自备正确的 UTF-8 环境（兜底见 E07）。

## Step: E02 生成评审说明

> - **输入**：验证阶段落盘的测试证据 + 方案文档 + 代码 diff
> - **输出**：一份评审说明文件，且格式校验通过
> - **失败时**：校验器报「输入/配置不可用」→ STOP 回报；报「某段没写好」→ 补那段重跑
> - **完成标准**：格式校验返回 0

说明由固定几段构成：改了什么 / 为什么 / 怎么改 / 测试情况 / 元信息。其中「测试情况」和
「元信息」由脚本从验证阶段的落盘数据**确定性渲染**，你不要手写、也不要美化 —— 它证明的是
「这次改动是否经历过自动验证、那次验证有多夯实」，不是覆盖率数字。你只负责写前三段。

⚠️ 落盘路径要带上本次运行的唯一标识，**不要用固定文件名**。两个并行的运行若写同一个固定
路径，会**静默互相覆盖**：你渲染完、手写好前三段，另一个运行的渲染又覆盖同一文件，你接着
把别人的正文当自己的传上去 —— 而格式校验照样全绿，因为文件本身合法，只是内容是别人的。

校验器的返回码是硬闸：0 才能往下走；非 0 且是「某段没过」就修那段重跑；是「配置/输入坏了」
就停下回报，别硬闯。校验没过**禁止**进入后面的推送步 —— 写在散文里的「务必」在上下文压力
下绑不住执行者，所以约束落在返回码上。

## Step: E03 评审说明长度守卫

> - **输入**：E02 生成的说明文件
> - **输出**：长度落在配额内的说明
> - **失败时**：超限由渲染器按固定顺序降级，不要临场决定砍哪段
> - **完成标准**：总长与每段都在配额内

每段有各自的字符配额，由校验器执行。总长超限时，渲染器按**预先定好的固定顺序**降级：先
折叠测试明细、再截「怎么改」、再截「为什么」，而强度说明与结论**永不删**；降级发生时会在
错误输出里明说，据实转述、不要隐去。固定顺序是重点 —— 从前靠执行者临场决定砍哪段，导致
同类信息在这个评审里留着、下一个里就消失了。

## Step: E04 🚦 提交前确认门

> - **输入**：待提交的 diff + E01 的提交信息
> - **输出**：一条被如实记录的确认决定
> - **失败时**：被守卫拦住时不要动守卫、不要伪造门 —— 理由见 topic `never-forge-a-gate`
> - **完成标准**：确认门已记录（本次无提交的纯本地交付可豁免）

这是提交前的**人工确认门**，也是这一阶段第一个真正把人拉进来的地方。做法：

🚦 **停在这里**。把这次要提交的东西摊开给人看 —— 改了哪些文件、diff 的要点、提交信息长
什么样 —— 然后**结束这一轮**，等人真的回话。不要自问自答，不要替人点头。

⚠️ **不要在同一轮里自己记录这个门。** 背书机制会检查「距上一次门之后有没有新的人类发言」，
如果你在没有新人类回复的情况下就记录了通过，它会识别为伪造并拒绝。正确的节奏是两轮：这一
轮只把门摆出来、结束；人回话后的下一轮才记录决定。

⚠️ **记录证据时要写人的原话，不要写你的转述。** 转述会悄悄改变语义 —— 把「可以，但先看看
X」压成「可以」，把一个带条件的同意变成无条件放行。原话保留了那个条件，你的复述会丢掉它。

若配置显式预授权了自动确认，可免去这一轮等待、直接记一条 auto 决定并往下走 —— 但那需要
对应的授权开关为真，否则记录会被拒绝。默认（未授权）永远走「停下来等人」这条路。提交属于
**可逆、且决策只依赖已知 diff 与信息**的动作，所以「配置默认放行」在这里是安全的；这跟不可逆
的生命周期动作不同，不要混为一谈。

## Step: E03b 历史评审人推荐

> - **输入**：当前代码库路径
> - **输出**：一个建议评审人 + 可选的反对证据
> - **失败时**：历史数据不可用 → 退到首选评审人，别自己去翻提交历史拼
> - **完成标准**：脚本输出已贴进对话供人过目

跑脚本拿建议，**不要**自己去翻提交历史猜评审人。建议恒为首选评审人；脚本再查本流程自己
记录的历史，**只用来产出反对证据**：若首选从没在这个库出现过、而某个别的人几乎包揽了这个
库，就仍取首选、但附上反对证据供人在下一步覆盖。

⚠️ 数据源是本流程自己的记录，不是提交历史 —— 提交历史里根本没有评审人别名（只有评审链接），
想从那里拿得对每个评审发一次网络请求。归组时要按**包名**归一，别按原始路径：隔离机制下每个
运行的路径都唯一，按路径分组会让每组只有一行、谁都不像重复出现过。

## Step: E05a 🚦 评审配置确认门

> - **输入**：E03b 的评审人建议 + 交付方式
> - **输出**：一组评审配置（评审人、是否发布、是否自动合并、是否自动修复、等待策略）
> - **失败时**：非评审类交付直接跳过本步
> - **完成标准**：配置已确认（或按预授权自动取用）

推送前对关键选项的**最后一瞥**：用哪个分支、评审人是谁、要不要发布、要不要自动合并。默认
**留在当前分支、不新建分支**；评审人默认首选，若上一步查到反对证据则在此浮现供覆盖。若配置
预授权了自动确认，就直接用已持久化的这组值、记一条 auto 决定；否则仍摆出一个轻确认门。
注意：自动合并由**独立开关**控制，免这道确认**不会**导致自动合并。

## Step: E06 交付方式判定

> - **输入**：方案文档的交付方式字段
> - **输出**：本次走「提交+推评审」/「只提交」/「不提交」中的哪条
> - **失败时**：字段缺失 → 停下来问，别默认最重的那条
> - **完成标准**：交付方式已确定

从方案里读交付方式：评审类 → 提交并推送评审；只提交类 → 只提交；纯本地类 → 连提交都跳过。后面几步的行为都由它分叉，务必先定清楚。

## Step: E07 提交并推送评审

> - **输入**：确认过的提交信息、评审说明、评审配置
> - **输出**：一个提交哈希 + 一条评审记录，并把推送落盘到完成不变量
> - **失败时**：提交失败重试；推送失败带正确参数重试
> - **完成标准**：提交存在、评审已创建、推送已记录

按顺序做：确定分支（默认留在当前分支，**禁止**在没经上一步披露+确认的情况下擅自建/切分支
—— 擅自建分支往往是用户不想要的、要返工）→ 暂存方案清单里的文件 → 提交 → 检查是否只多出
本次这些提交 → 推送到评审系统。

⚠️ **暂存前必须重新读一次仓库状态**：先前的状态快照不耐久。共享工作树下索引可能已经长出
别人的暂存条目 —— 这时提交会把别人的改动扫进本次评审，而重置又会毁掉别人的暂存，**两者对
第三方都有破坏性 → 停下来回报，一个 git 写都不要做**。

⚠️ 推送时**务必把 E02 的评审说明文件当参数传进去**，否则那份精心生成、校验过的说明一个字
都不会出现在评审上 —— 评审工具会自己从提交信息猜一份顶替。推送成功后**立即**把评审号与
修订号记进完成不变量：这是「最新推送到第几修订」的一半，后续观察阶段要核对同一修订，漏记
会让后面的完成判定失败（提前完成被结构性挡住）。

## Step: E07b 阶段评分上报

> - **输入**：本阶段各步状态 + 关键指标（提交哈希 / 评审号 / 评审人）
> - **输出**：一条阶段评分记录，交棒到观察阶段
> - **失败时**：脚本报错 → 回报，不要跳过
> - **完成标准**：评分已 emit、交棒标记已写

本阶段末步：跑脚本上报这一阶段的评分与关键指标，并标记交棒给下一阶段（观察）。机制细节见
对应参考文件，这里照实调用即可。
