# 变异验证的两个失效陷阱

变异验证（去掉修复 → 测试必须红）本身可能是假的。两个实际踩过的坑：

## ① 变异打错了位置

用 `str.replace(old, new, 1)` 做变异时，如果 `old` 在文件里出现多次，
你替换的是**第一次出现**，可能根本不是你想改的那处。

真实案例：验证一个「关闭步骤时自动跳过互斥兄弟」的守卫，变异锚点
`grp = f.group_of(s.id)` 在两个函数里都有，而另一个函数在文件中更靠前。
变异打到了无关的地方，**测试全绿**，差一点把「未被测试的守卫」当成「已验证」上报。

**做法**：变异前先 `grep -n <锚点>` 确认命中几处。多于一处就把锚点扩大到唯一。

## ② 陈旧的字节码

同长度的 token 互换（`gate` ↔ `auto`、`True` ↔ `Fals`）+ 一秒内改回，
会留下 CPython **永远认为有效**的 `.pyc`——因为时间戳失效检查只比对 mtime 和 size，
两者都没变。

如果 `PYTHONPYCACHEPREFIX` 被设置（有些运行环境会设），字节码存在**源码树外**，
清理 `./__pycache__` 根本碰不到它。

**做法**：变异验证的清理步骤要同时清树内和 `$PYTHONPYCACHEPREFIX`。

## 一个更一般的教训

这两个坑的共同点：**验证机制自己失效时是静默的**。
所以「变异后测试变红」这个结论也需要证据——至少要看到红的是**你预期的那条测试**，
而不是只看总数变了。
