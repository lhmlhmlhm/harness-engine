# Context 阶段：动手之前，把事情弄清楚

这是整条流程的第一层，目的只有一个：**在改动任何一行代码之前，把「要改什么、为什么改、改了会牵连到谁」彻底摸清，并且跟发起人当面对齐。** 它不产出代码，产出的是一份被人确认过的执行方案，加上一组「这些前置事实此刻仍然成立」的校验结论。

这一层最大的价值不在于跑完多少步，而在于**拦住那些一开始方向就错的活儿**——诊断没做透、方案有两种读法却自己挑了一种、依赖还没就绪就往下冲。这些错误越往后越贵。

做完的标准：起始横幅已打出、前置事实校验通过、方案已经过人确认（或被明确预授权免确认）、初始进度已落进持久化状态库，然后才交棒给下一层。

---

## Stage: activation — 激活

### Step: C00 激活横幅
> - **输入**：本轮的触发信号（任务上带着「需要走本流程」的标记，或发起人直接说「提交 / 发布」）。
> - **输出**：一行激活横幅，末尾带上本次加载的历史经验条数，并逐条列出经验 id。
> - **失败时**：经验库查询脚本**不存在**是合法情形（该项目没装），横幅照打、条数记 0 即可；但脚本**存在却报错**（库被锁 / 崩溃）属于环境不稳，应停下来交回给人，不要伪造成 0 继续。
> - **完成标准**：横幅作为本阶段第一条叙述输出打出，且只打这一次。

这必须是你的**第一条叙述输出**。允许在横幅之前先静默跑一次本地经验查询——它是本地快查、无网络，是横幅的数据准备，不算「叙述」。拿到真实条数和明细后，**一次性**把完整横幅打出来。

最容易错的地方：在查询还没返回时先打一个「加载中…」占位横幅，结果横幅显示两遍；或者凭印象手写一个条数。条数必须来自脚本对库的实际计数。横幅之后，从触发上下文里解析出本次运行的唯一标识（多级回退，取不到才现场生成）。

## Stage: resume — 续跑对齐

### Step: C01 方案文档状态迁移
> - **输入**：任务描述里指向方案文档的路径（取不到就用别名去搜）。
> - **输出**：方案文档状态从「已排期」迁到「进行中」，并移动到对应目录。
> - **失败时**：路径含特殊字符导致读失败时，依次换用直接读 / 加引号读 / 模糊搜三种方式；**全都失败就报错停下，绝不能默默跳过整条流程**——没有方案就没有可执行的依据。
> - **完成标准**：找到方案文档并完成状态迁移。

读到方案文档后，如果它声明了「工作区隔离」，此处会顺带开一个独立工作区和专属分支，让本次改动与主工作树互不干扰。这一步一旦失败就硬失败、绝不悄悄退回共享工作树——因为悄悄退回，恰恰就是隔离功能想消除的那个失败模式。隔离细节见 topic `worktree-isolation`。

### Step: C02 并发检测与续跑硬重锚
> - **输入**：持久化状态库里的活跃运行表 + 锁文件；本次运行标识。
> - **输出**：确认没有另一个进程在同标识下同时跑；若是续跑，则重新把状态机锚定到正确的当前层。
> - **失败时**：同标识已有活跃进程持锁 → 停下（防双跑）。续跑时**不要凭记忆重建进度**，一律用脚本对账状态库。
> - **完成标准**：无并发冲突，且（若续跑）已补齐所有「到达过但没收尾」的层。

续跑边界是漏报的重灾区：单段会话里从头跑到尾的层通常都正常收尾，唯独那些**跨了上下文压缩、需要多轮才完成的层**（典型是要等外部检查的观察层）容易被孤立——你「以为」它做完了，其实它的小结从没打出来。所以这里强制用确定性对账取代记忆重建。对账脚本会明确告诉你哪些层还欠小结、以及该重新锚定到哪一层，照着做，别自作主张往前跳。

## Stage: pre-flight — 前置校验

### Step: C02b — 工作树形态

隔离一个工作树是**效果**，不是计算。引擎不做它：脚本由你来跑，引擎随后用只读 git 去问世界
到底怎样。这个分工不是洁癖 —— 它是「我隔离了」这句话唯一能被反驳的安排。

源实现把它要消除的失效模式写得很清楚：provisioning 失败时**硬失败、绝不退回共享工作树**，
因为静默退回「会把调用方明确要求隔离掉的那个行为原样交回去，同时报告成功」。一句没人核对的
「已隔离」就是同一个退回，只是上移了一层 —— 记录说隔离了，而工作仍然发生在主树上，
而两者在日志里长得一样。

判断的依据是两件可独立观察的事：链接工作树的 `.git` 是**文件**（指向拥有它的仓库），
而源检出的 `.git` 是**目录**；隔离分支形如 `shipcheck/<短 id>`。所以「已隔离」这句声称由
「这个目录不是链接工作树」反驳。

反过来那一句也要核。「按方案声明留在共享树」是完全正当的形态（开关关掉时本段不适用），
但如果它不可核对，它就是跳过隔离的免费出口 —— 所以它由方案文档里声明的 `worktree_isolation`
反驳：方案说要隔离而你说留在共享树，两者不能同真。

**不要 `git checkout -b`。** 隔离分支已经存在，且工作树已经 checkout 在它上面；切分支恰好
破坏你刚建立的隔离。

**完成标准**：工作树形态已记录（`isolated` / `shared_declared`），且该记录经独立事实核实未被反驳。

### Step: C03 前置事实的时效检查
> - **输入**：方案文档里记录的「已核实事实」及其核实时间戳。
> - **输出**：一个判定——这些事实此刻可信 / 需抽查 / 已过期。
> - **失败时**：没有时间戳字段，就当作必须重新核实关键路径。
> - **完成标准**：给出时效判定并据此决定下一步。

规则很简单：核实时间在一天内直接信任；一天到一周之间，抽查关键路径；超过一周，停下——代码很可能已经漂移，旧结论不能拿来当依据。这一步防的是「拿着上周的地图走今天的路」。

### Step: C04 代码同步
> - **输入**：当前工作区与远端的差距。
> - **输出**：落后就同步到最新，本来就干净则跳过。
> - **失败时**：同步出现冲突时停下交人处理，不要强行覆盖。
> - **完成标准**：工作区不落后于远端，或确认无需同步。

### Step: C05 前置事实逐条核验
> - **输入**：方案里列出的关键路径清单（每条形如「路径」「路径:行号」或「路径:行号（标注）」）。
> - **输出**：逐条去代码里查证，全部命中才算过。
> - **失败时**：任意一条查不到 → 停下。方案建立在这些锚点上，锚点错了方案就是空中楼阁。
> - **完成标准**：清单全部命中。

### Step: C06 平台特性缓存查询
> - **输入**：当前工作区所属的包与平台。
> - **输出**：命中已知平台特性时，把编译/测试命令的覆盖值缓存给后续层用。
> - **失败时**：查不到就按默认命令走，不阻塞。
> - **完成标准**：完成一次查表，命中则缓存。

有些包在特定平台上有已知的坑（比如构建命令要换个写法）。此处提前查一遍，把该用的命令备好，省得后面的层各自踩一遍同样的坑。

### Step: C07 跨任务依赖检查
> - **输入**：方案里声明的上游依赖（若有）。
> - **输出**：确认每个上游都已发布/完成。
> - **失败时**：任一上游未就绪 → 停下，别在依赖悬空时往下冲。
> - **完成标准**：所有上游依赖状态为已就绪。

判断上游状态**只认方案文档和任务系统里的状态字段**，不要拿任务描述的正文、勾选框、或当初排期时写下的依赖备注来判断——那些都是会过期的旧快照。

## Stage: understanding-gate — 理解门

### Step: C07b 诊断挑战
> - **输入**：复杂任务的问题诊断（现象 / 根因 / 影响面）。
> - **输出**：经过质疑、被证伪过一轮的诊断结论。
> - **失败时**：诊断经不起挑战，就退回去重新查，别硬把薄弱结论推进下一层。
> - **完成标准**：诊断挺过了 M1/M2/M3 三轮质疑。

只对复杂任务做。派一个「唱反调」的角色专门挑诊断的毛病：根因是不是想当然？影响面是不是漏了？现象和根因的因果链站得住吗？这一步存在的意义是：**在方案定型之前，先把它当成靶子打一遍**，比让人在确认门那里替你发现漏洞要便宜得多。

---

## Stage: plan-confirmation — 方案确认

### Step: C08 问题诊断
> - **输入**：任务要解决的问题。
> - **输出**：现象、根因、影响面（附查证结果）。
> - **失败时**：根因说不清就别急着列方案，先查透。
> - **完成标准**：三要素清晰、有证据支撑。

方案确认的开场。把「发生了什么、为什么发生、会波及哪里」讲清楚，影响面要有实际查证的结果撑腰，不能靠猜。

### Step: C09 方案选择
> - **输入**：针对根因的候选解法。
> - **输出**：多解法时列出对比；确定性修复可跳过。
> - **失败时**：候选之间取舍不清时，摊开利弊交人定，别替人默默选一个。
> - **完成标准**：方案唯一确定，或对比清单已备好待确认。

### Step: C10 改动明细
> - **输入**：选定方案。
> - **输出**：一张改动表（路径 / 操作 / 锚点 / 手动还是自动）。
> - **失败时**：锚点定不下来的行，标出来别硬填。
> - **完成标准**：每处改动都能对应到具体位置。

### Step: C11 调查严谨度检查
> - **输入**：含数值断言或涉及多条路径的改动。
> - **输出**：穷尽式查证的结果，确认没有漏网的同类点。
> - **失败时**：查证不全就不要下「就这些」的结论。
> - **完成标准**：同类点已穷尽、数值有依据。

只要方案里出现「一共 N 处」这类数值断言，就必须穷尽查一遍，不能凭手头看到的几个就下结论。

### Step: C12 解析样本核验
> - **输入**：改动里用到的正则 / 批量替换规则。
> - **输出**：拿真实样本喂一遍，确认匹配范围既不多也不少。
> - **失败时**：样本里出现误伤或漏匹配 → 收紧规则再验。
> - **完成标准**：规则在样本上表现符合预期。

批量替换最容易「顺手多改一个」或「差一个没改到」。别信眼睛，拿实际内容跑一遍看命中集。

### Step: C13 自环检查
> - **输入**：本次改动，以及后续验证要用的命令。
> - **输出**：确认「被改的东西」和「用来验证的东西」不是同一个。
> - **失败时**：发现验证会用到被改对象 → 换一个独立的验证口径。
> - **完成标准**：验证与改动相互独立。

防的是「用改过的尺子量改过的布」——那种验证永远会通过，却什么都没证明。

### Step: C14 方向确认
> - **输入**：改动明细。
> - **输出**：明确「事实来源」和总体改动方向。
> - **失败时**：方向和事实来源对不上就停下来核。
> - **完成标准**：改动方向与权威来源一致。

### Step: C15 影响分析
> - **输入**：改动涉及的对象。
> - **输出**：一张下游依赖状态表——谁会因此受影响。
> - **失败时**：下游关系摸不清时，先补查再往下。
> - **完成标准**：下游影响已列全。

### Step: C16 风险声明
> - **输入**：本次方案。
> - **输出**：风险点 + 每个风险的回退路径。
> - **失败时**：想不出回退路径的风险，要显式标为「不可逆」提醒发起人。
> - **完成标准**：风险与回退都写明。

### Step: C17 模糊逻辑检查
> - **输入**：涉及模糊匹配 / 阈值 / 启发式判断的改动。
> - **输出**：把这些「非确定」逻辑显式标出来。
> - **失败时**：拿不准某段逻辑是否属于此类时，宁可标出来。
> - **完成标准**：模糊判定点已全部点名。

### Step: C18 多路径消歧
> - **输入**：一个符号/名字在代码里有多处落点的情形。
> - **输出**：明确这次到底改的是哪一处。
> - **失败时**：分不清目标路径就别下手，先消歧。
> - **完成标准**：目标路径唯一、无歧义。

### Step: C19 历史经验召回
> - **输入**：本次改动的关键词。
> - **输出**：召回相关的历史解法与反面教训，展示给发起人；命中就列出，未命中则跳过。
> - **失败时**：经验库不存在是合法情形，跳过即可；存在却报错则停下交人。
> - **完成标准**：完成一次召回，并（若命中）随后重算经验热度。

召回既是给人看的（别重犯老错），也顺带刷新了这些经验的使用记录。召回完紧接着重算一次经验热度，让下一次运行的起始横幅能反映最新情况——这一步幂等、安全、可逆，不需要额外确认。

### Step: C20 🚦 方案确认门（需人确认）
> - **输入**：以上 C08–C19 汇总出的完整方案（诊断、改动明细、影响、风险、召回）。
> - **输出**：发起人对方案的明确表态——同意 / 要改 / 取消。
> - **失败时**：得不到明确表态就停在这里等，**绝不能把「没人反对」当成「已同意」**往下冲。
> - **完成标准**：拿到「同意」这一确定信号（或读到显式预授权配置）后才放行。

这是整个 Context 层的**承重点**。前面所有查证、诊断、明细，都是为了让发起人能在这一刻做出一个知情的决定。

流程上有两条分支。一是**预授权免门**：如果发起人此前已通过配置显式授权「方案自动确认」（且方案确实是新排期、前置事实也新鲜），就打一行「已按预授权确认」直接放行——但注意这只在**确实存在那条授权配置**时成立，绝不能因为「看起来没问题」就自行免门。二是**正常确认**：打出确认门提示，然后**结束本轮、把手交回给人**，等他回话。

这里有两个反复出现的自欺陷阱，务必警惕。其一，**把沉默读成同意**：人没回话不等于人点头，那只说明你还没拿到信号，该继续等。其二，**在确认之前先把方案上传给评审方**：确认门提示打出**之前**，要先把方案上传到评审面板，让远端评审能在人点头**之前**就看到方案——因为一旦本轮停在这个门上，层末尾那些「收尾才跑」的动作就不会执行了，等于永远不上传。为此，即便走了预授权免门分支，这次上传也照样要做（供审计）。这条上传有幂等安全网，漏跑会被自动补触发，但**理想路径是你主动先传**。判断标准写死在工具里而不是靠这段散文口头约束，因为一句「务必要问」并不能真正拦住一个赶进度的执行者——真正的门是工具记录的那个确认动作。

### Step: C21 反射式接口暴露检查
> - **输入**：涉及「把接口 schema 暴露给模型」的改动。
> - **输出**：确认暴露面符合预期。
> - **失败时**：暴露面不清时停下核对。
> - **完成标准**：schema 暴露已审。

仅当改动触及会向模型暴露 schema 的那类工具时才做。属于窄条件下的专项检查，详见对应 topic。

### Step: C22 初始进度落库
> - **输入**：本次运行的标识、方案槽位、工作区、交付形态、复杂度。
> - **输出**：确认持久化状态库里已建好本次运行的记录行。
> - **失败时**：回读不到记录行 → 停下查状态机，别在没有权威进度源的情况下往下跑。
> - **完成标准**：状态库记录行存在且可回读。

进度的**唯一权威源是持久化状态库**，不再往文件里写快照。本步只做一件事：确认那一行确实建好了、能回读出来。之所以强调单一权威源，是因为进度散落在多处时必然会漂移、最后谁都不知道到底跑到哪了。

### Step: C24 层评分上报
> - **输入**：本层实际执行过的步骤清单 + 度量（复杂度、前置校验结果）。
> - **输出**：本层的评分与交棒信号。
> - **失败时**：上报机制不可用时按 topic 约定处理，别默默略过。
> - **完成标准**：分数已 emit，交棒给下一层。

Context 层的末步。把本层做了哪些、结果如何汇成一个分数发出去，并显式标记交棒。
