# Report 阶段：把判断变成一份能被行动的东西

报告的读者是**明天的你**。所以它不是判断的转录，而是一份「哪些事需要处理、哪些已经很好、以及这次看的范围有多大」的清单。

范围要写在最前面，而且要包含缺口。一份没说清覆盖范围的复盘，读者无法判断「没提到 X」意味着「X 没问题」还是「X 没被看」。

---

### Step: R01 产出报告

写成一份 markdown，路径记成 `report_path`，再记一条三行以内的 `report_summary`。

结构固定为四段：

```
## 窗口与覆盖
   login / 日期范围 / 每天的结局（has_commits / empty / no_snapshot）
   commit 总条数 / package 数 / 跨包关联组数
   ⚠️ 任何 no_snapshot 的日期都要在这里点名 —— 那是数据缺口，不是「没干活」

## 按 package 逐条
   每个包一小节，包内每条 commit 一条：subject + CR 链接 + 三问的结论
   结论要短。细节留在 verdict 的 evidence 里，报告是索引不是转录

## 跨包一致性
   每组关联一条。没有关联就写「本窗口没有跨包关联」，并说明是查过之后的结论

## 需要跟进
   只放需要动手的。每条给出：在哪个包、哪一条 commit、具体做什么
   没有就写一句「没有」
```

**「需要跟进」必须是一个独立小节，而且标题就是这四个字。** 关掉这一步时引擎会按这个锚点把那一节原文交回来（`output`），所以：

- 改了标题 → 交回来的是 `selector_no_match`，不是内容
- 删掉整节 → 同上
- 没有需要跟进的 → 在那一节里写「没有」，**不要删掉小节**

这条设计是刻意的：让「这次复盘的产出是什么」在关步骤的那一刻就直接可见，而不用再去开一次文件。而它**不承重** —— 交回失败不会让这一步关不掉（那是 `output` 的设计），所以不要把交回成功当成报告写对了的证据。

---

### Step: R02 收尾

告诉用户两件事：**报告在哪**，以及**有几条需要跟进**。

判据是「没有未处理的 violation」。如果有，先说清是什么再处置——不要为了让这个 run 干净而静默关掉它。`harness audit` 会把它们列出来，而它们在这条流程里通常只有一个来源：某一步被强推过。那件事值得出现在报告里，因为它说明这次复盘的某一段是没有判据托着的。

关 run：

```sh
harness close-run --run <id>          # 默认 completed
harness close-run --run <id> --result abandoned
```

`abandoned` 用在「窗口里根本没有可复盘的东西」之外的情形——**空窗口本身不是 abandoned**，它是一次完整的、结论为「这段时间没有合入」的复盘，应当 `completed`，并且报告里要写清楚那不是数据缺失。
