# Gather 阶段：把一段时间的 commit 变成可逐条处理的集合

这一层不做任何判断。它只回答三个问题：**窗口是什么、那几天各自发生了什么、这些 commit 按包怎么分**。

之所以把取数单独成一层，是因为后面「逐条判断」的判据直接绑在这一层的产出条数上：verdict 的条数必须 >= commit 的条数。如果这一层含糊，后面那条判据就在一个含糊的集合上成立——它仍然会通过，但通过的是一件更小的事。

**这一层最容易出的错，是把三种「没有」混成一种。**「那天没有采集快照」「那天有采集但你没提交」「那天你提交了但都在本地仓库」是三件不同的事，处置也不同：第一件要换日期或说明数据缺口，第二件是正常结论，第三件说明这个数据源看不到你那部分工作。所以 `day_snapshot` 的取值是一个封闭枚举，而不是自由文本。

---

### Step: A01 确认窗口（谁、哪几天）

**先读配置，不要凭记忆。**

```sh
harness config --run <id>
```

它会把 `login` 和 `days` 连来源一起打出来（`run` 表示这次覆盖过，`flow-default` 表示用的是默认值）。单次覆盖：

```sh
harness config --run <id> --set login=someone --set days=1
```

`days` 的默认值是 7 而不是 1，这是量出来的：单日快照经常为空——本地仓库（`~/.kiro/skills` 一类）的工作不进 GitFarm，所以一个只看一天的默认值经常空手而归，而那看起来像机制没在工作。

然后把窗口摊平成**逐日**的一串 `day_requested`。为什么不记一条「7 天」了事：下一步的判据是「取到的天数 >= 应取的天数」，而「应取几天」只有这一步知道。记成一条区间，那条判据就退化成「取到过至少一天」。

日期用 UTC+8 的 `YYYY-MM-DD`，因为数据源就是按这个口径采集的。

---

### Step: A02 逐日取快照

一天一次调用，一天一条 `day_snapshot`：

```
query_commits(date="2026-09-08", login="<login>")
```

三种结局，取值只能是这三个之一：

| 取值 | 什么情况 | 怎么处置 |
|---|---|---|
| `has_commits` | 返回了 commit 列表 | 进 A03 |
| `empty` | `commits: []` 但有快照 | 正常结论，记下就行 |
| `no_snapshot` | 返回 `{"status": "no_snapshot"}` | **数据缺口**，要在报告里点名，不要当成「那天没干活」 |

**不要为了省调用次数改成一次取全团队再筛自己。** 团队级返回把所有人的 commit 连完整 body 一起带回来，一次可能是 20K+ tokens，而你只要其中一个人的。按 login 逐日取是又准又省的那条路。

---

### Step: A03 把每条 commit 落成一行

每条 commit 一条 `commit`。值里至少要有：`package_name`、`subject`、以及 body 里那条 `cr:` 链接。这三样是后面判断和写报告都要用的。

**逐日核对条数**：某天快照里有几条，你就该记下几条。这一步是 `attest` 而不是机器判据，原因写在 flow 的头部注释里——引擎手上没有第二个来源可以反驳你。所以这里的诚实程度，决定了后面那条「判了几条」的判据是在多大的集合上成立。

body 通常很长（几百到上千字），而且写得很详细——它往往已经把「为什么这么改」「为什么不那么改」说清楚了。**不要把 body 全文抄进 evidence 的值里**：值只放定位信息，body 在判断那一步按需重读。

---

### Step: A04 按 package 分组

每个出现过的 package 一条 `package_group`，值里带该包的 commit 条数。所有条数加起来应当等于 `commit` 的行数——这是一个你可以自己核的等式，核一遍比事后发现分组漏了一个包便宜。

分组按 `package_name` 字面分，不要按「我觉得它们是一个东西」合并。前端和 BFF 是两个包，它们的关联是下一步的事。

---

### Step: A05 找出跨包关联

关联的依据**只能用可核对的东西**：

- 同一条 `cr:` 链接出现在两个包的 commit 里
- 某条 commit 的 body 里点名了另一个包、另一个 CR、或另一条 commit
- 同一天、同一个功能名，而且 body 互相呼应

实测这种关联在数据里是**看得见**的：同一天里前端包和 BFF 包各有提交，而 body 会直接写「the frontend sender is a separate change; this one only opens the write path」——那就是一个可核对的关联依据。

**不要凭「听起来相关」建立关联。** 一个编出来的关联会在下一步产出一个编出来的判断，而那种判断读起来和真的一样。没有关联就记零条，并在 attest 里说明你查了什么、为什么判定没有。
