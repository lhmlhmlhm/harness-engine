# Derive 阶段：从收集到的素材里推导出分类维度

这是方案生成的第二层，接在收集层之后。目的是**把上一层收拢的素材，推导出两个能被机器消费的分类维度——tags 与 scope**，并在确实复杂时补一轮并行调研。它不产出方案正文，产出的是给方案打标、供下游按维度检索和归属的元信息。

这一层的关键不是「打了多少标」，而是**每个推导结果都要能被下游区分出它的来路**——尤其 scope，「被认出来」和「落到兜底」在结果里长得可能一样，必须显式标清（见 `D02`）。

三步都是共享核心（所有变体通用）；其中 `D03` 是可选的，只有复杂到需要并行调研时才做。

---

## Stage: derive — 分类推导

### Step: D01 推导 tags
> - **输入**：收集层登记的不确定项与工作区线索。
> - **输出**：本方案的 tag 集合。
> - **失败时**：推导不出任何 tag 是允许的，但要显式记成空集，不要留空当作「还没做」。
> - **完成标准**：tag 集合已记录（空集也算，但必须是显式的空集）。

tags 是由分类规则表**从工作区自动推导**出来的，不是手填的。它让下游能按标签把相关方案聚到一起。

最容易错的地方：**手填 tag**，或者推导出空集时干脆把这一步留白。手填会绕开唯一事实源，填出规则表里不存在的标签，下游按标签检索时对不上。而留白和「显式空集」在存储里是两回事——留白无法和「这一步还没跑」区分开，下游不知道是真没标签还是漏做了；显式的空集才是一个明确的「推导过了，结论是没有标签」。所以哪怕结论是空，也要把它当成一个正经结论记下来。

### Step: D02 推导 scope
> - **输入**：`D01` 的 tags 与工作区线索。
> - **输出**：本方案的 scope，以及它是**被规则表认出来的（derived）**还是**落到了兜底（fallback）**。
> - **失败时**：分不清是命中还是兜底时，按兜底记——把命中误记成 derived 比诚实标 fallback 危害大。
> - **完成标准**：`derived` / `fallback` 二者之一已记录。

scope 标明本方案归属的范围。判据只认两个值，而它们的重点不在 scope 具体是什么，而在**这个 scope 是怎么来的**：

- `derived`——分类规则表**认出了**这个工作区，明确判定了它的归属。这是有依据的归属。
- `fallback`——规则表**没认出来**，用了一个兜底的默认归属。这是「没依据、姑且如此」的归属。

必须区分这两者的原因是：**如果不标来路，一个被认出来的 scope 和一个兜底的 scope 在下游长得一模一样**——都是一个 scope 字符串。下游便无从判断这个归属是可信的判定，还是一个未经确认的默认值。而这两种情况下游该采取的动作不同：`derived` 可以直接信任，`fallback` 则是一个信号——说明这个工作区还没被规则表覆盖，可能需要有人去补一条规则，或者至少不该把这个归属当成确定结论去做下游决策。

最容易错的地方：**只记 scope 的值，不记它是 derived 还是 fallback**，或者干脆把兜底也乐观地标成 derived。前者让下游丢掉了判断可信度的唯一线索；后者更糟——把「没认出来」粉饰成「认出来了」，下游会拿一个其实没依据的归属去做本该只对确认归属才做的事。分不清时按 fallback 记，因为诚实地说「没认出来」永远比虚报「认出来了」安全。

### Step: D03 并行调研（仅复杂场景）
> - **输出**：若本次复杂到需要并行调研，给出各路调研的结论。
> - **失败时**：确定性场景直接跳过本步，不要为了「显得充分」硬凑调研。
> - **完成标准**：至少两条调研结论（只有一条，说明本就不需要并行）。

这一步是**可选**的。只有当本次方案复杂到「有多个相对独立的方向都需要摸清」时，才值得并行铺开去调研；铺开了就会有多路结论汇回。

最容易错的地方有两个，方向相反：一是**该做时不做**——复杂任务不铺调研，靠拍脑袋往下写方案；二是**不该做时硬做**——确定性的简单场景，为了让方案「看起来调研充分」而强凑几路调研。判据要求「至少两条结论」正是对第二种的防线：并行的意义在于同时推进多个独立方向，如果你只能凑出一条结论，那根本不存在「多路」，也就不需要并行——直接跳过这一步，而不是把一条结论掰成两条来凑数。跳过它是完全正当的，可选就是可选。
