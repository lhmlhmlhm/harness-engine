# Gather 阶段：把散乱的输入收拢成结构化素材

这是方案生成的第一层。目的只有一个：**在动手写方案正文之前，把发起人零散抛过来的诉求、背景、顾虑，收拢成一组有确定形状的素材**——它属于哪一类方案、走哪个变体、目标背景约束各是什么、哪些还没定、以及本变体特有的那几块专属字段。它不产出方案文档本身，产出的是喂给后续「推导」和「成文」两层的原料。

这一层最大的价值，不在于把表填满，而在于**把「还没想清楚的」和「已经坐实的」分开摆**——尤其是把假设和已验证事实分两栏登记（见 `G04`）。收料阶段图省事把两者混在一起，是后面所有返工的源头。

做完的标准：方案类型、executor、通用四块、不确定项处置，以及本变体的专属字段块，全部落进持久化的证据里，才交棒给推导层。

前四步（`G01`–`G04`）是所有变体共用的核心；第五步分裂成一对互斥形态——代码类走 `G05sc`，设计类走 `G05ux`，两者只会执行其一。

---

## Stage: classify — 定性与定向

### Step: G01 场景识别（选模板）
> - **输入**：发起人这次抛过来的原始诉求。
> - **输出**：本次属于哪一类方案——变更提案 / 特性规划 / 重构规划 / 配置变更 / 调查 / 复合。
> - **失败时**：吃不准是哪一类时，宁可归到「复合」，也不要自造一个枚举外的类型。
> - **完成标准**：类型已记录，且取自那个封闭枚举（六选一）。

方案类型决定了后面用哪个模板、哪些字段必填，所以它必须落在一个固定词表里，让下游能拿它去精确匹配模板。

最容易错的地方：**自造类型**。看到一个诉求既像改配置又像修 bug，就顺手写个「配置修复」这种词表里没有的名字。下游是拿这个字符串去查表选模板的——查不到就静默落空，既不报错也没有模板，你要到成文时才发现整份方案没有骨架。所以吃不准就归「复合」，那正是为「同时沾好几类」准备的兜底格，而不是让你在枚举外另起炉灶。

### Step: G02 Executor 识别（决定本次走哪个变体）
> - **输入**：`G01` 的方案类型，加上工作区/任务本身的线索。
> - **输出**：解析出的 executor（代码类走 ship-check，设计类走 ux），外加解析理由。
> - **失败时**：规则都没命中就落到默认，但要把「落到默认」这件事本身当作理由写下来。
> - **完成标准**：executor 与解析理由都已记录。

这一步决定第五步走哪个专属分支，也决定整个后续变体。关键约束：**分类规则表是唯一事实源**。executor 的取值词汇只有它说了算，不要在本流程里另抄一份 executor 清单——两份清单迟早漂移，届时同一个工作区在这里判成一个变体、在别处判成另一个，没人知道哪份对。

最容易错的地方：只记结果不记理由。光写「executor = ux」，下游没法判断这是**规则命中**得出的，还是**一条都没命中、落到默认**得出的。这两者可信度天差地别：命中是有依据的判定，落默认是「没依据、姑且如此」。判据里单独要一条 `executor_reason` 就是逼你把这个区别显式写出来——命中就写命中了哪条规则，落默认就老实写「无规则命中，取默认」。

## Stage: common-block — 通用块

### Step: G03 通用块信息收集（目标 / 背景 / 约束 / 待确认事项）
> - **输入**：`G02` 的定向结果，加上发起人给的全部背景材料。
> - **输出**：所有变体共用的那几块——目标、背景、约束，以及一份「待确认事项」清单。
> - **失败时**：一条待确认事项都列不出来时，先怀疑是不是还没想透，而不是当作真没有。
> - **完成标准**：目标、背景、至少一条待确认事项，都已记录。

目标说清「要达成什么」，背景说清「为什么现在做」，约束划出边界，待确认事项则收集「此刻还没定死的点」。判据只硬性要求目标、背景、以及**至少一条**待确认事项。

最容易错的地方：**把待确认事项清单交成空的**，并以为这是「这次特别清晰、真没有不确定」。真实情况几乎总是反过来——一条待确认都列不出，通常说明还没深入到会碰见分歧的程度，而不是分歧不存在。硬要求至少一条，就是逼你去把潜在的模糊点找出来摆上台面，而不是让它们藏着，等到成文甚至执行时才以「当初没说清」的形式爆出来。

### Step: G04 已知不确定项（与已验证事实分开登记）
> - **输入**：`G03` 收集到的待确认事项，以及方案里其它一切「假设成立」的依赖。
> - **输出**：每一条未定的假设/依赖，都带上一个处置结果——待解决 / 已解决 / 已有降级路径。
> - **失败时**：**绝不能把还没验证的假设塞进「已验证事实」那一栏**；分不清就一律按未验证登记。
> - **完成标准**：每一条不确定项都有处置结果（三值之一：待解决 / 已解决 / 已有降级）。

这是本阶段最该写透的一步。它要求你把每一条「我假设它成立」的东西单独拎出来，标明它现在的处置：还没解决、已经解决、还是虽没解决但备好了降级路径。

关键在于**这栏和「已验证事实」是两栏，物理上分开登记**。区别不是文书洁癖：

- 「已验证事实」是你**真的去查过、当场命中**的东西（下一步 `G05sc` 里会逐条实测）。
- 「不确定项」是你**假设成立、但还没查证**的东西。

一旦把一条假设写进「已验证事实」栏，下游读的人就把它当成板上钉钉的前提往下建方案——所有依赖它的设计、排期、验证清单都默认它为真。而它其实只是个没验证的猜测。**它会一直看起来没问题，直到执行到真正要用它的那一刻才炸**，那时方案已经成文、任务已经排期，返工代价最大。这正是判据只认那三个处置值、且把它和 `verified_fact` 分成两个不同 `kind` 的原因：让「假设」在类型上就不可能冒充「事实」。

最容易错的地方：图省事，把一条「应该没问题吧」的依赖直接记成已验证。省下的是这一步几分钟的查证，赔上的是下游拿假设当事实的全部连锁。

## Stage: variant-fields — 变体专属字段（二选一）

> `G05sc` 与 `G05ux` 是一对**互斥**形态，不是两个要都做的步骤。`G02` 判成代码类就只走 `G05sc`，判成设计类就只走 `G05ux`。读者看到这对平行步骤，第一反应往往是「怎么重复了」——它们不重复，是同一个位置在两个变体下收集的**不同种类**的专属字段。为什么字段种类不同，见下面每一步的说明。

### Step: G05sc 代码类专属字段（交付方式 / 测试豁免 / 已验证事实）
> - **输入**：`G04` 登记好的不确定项，以及本次代码改动的交付意图。
> - **输出**：交付方式 + 测试豁免类别 + 一组逐条实测命中过的前置事实。
> - **失败时**：任一「已验证事实」当场没查到，就不能记为命中——退回 `G04` 按不确定项处理。
> - **完成标准**：交付方式与测试豁免两个枚举都取自各自的封闭集合，且每条已验证事实都实测命中。

**这三块只属于代码类**，因为它们全是代码交付才有的语义：

- **交付方式**（提交并送评审 / 仅提交 / 不提交 / 仅本地）回答「这次改动最终怎么落地」。设计类的产出是设计稿与交接文档，没有「提交进代码库、送代码评审」这一路，所以这个字段对设计类没有意义。
- **测试豁免类别**回答「为什么这次可以不写/不跑测试」（无豁免 / 无测试框架 / 纯文档 / 纯配置 / 纯生成物 / 外部受阻）。这是给代码验证层看的——它默认要有测试，豁免是显式的例外声明。设计类根本不进代码验证层，谈不上豁免。
- **已验证事实**是逐条实测命中的前置锚点，直接对应 `G04` 里那栏「已验证」。

最容易错的地方：**把没当场查到的事实也记成 `hit`**。判据要求这一栏里每条的取值都是「命中」，意思是**你不该往这栏里放没验证的东西**——不是把所有假设都标成 hit 就能过。分不清一条到底查没查到，就把它退回 `G04` 当不确定项，别硬塞进来充数；这里放进一条假命中，等于给整份方案埋了颗 `G04` 极力要避免的雷。

### Step: G05ux 设计类专属字段（目标项目 / 参考输入 / 受影响产物 / 修订类型）
> - **输入**：`G04` 登记好的不确定项，以及本次设计修订的范围意图。
> - **输出**：目标设计项目 + 参考输入 + 预期会改到的产物 + 修订类型。
> - **失败时**：修订类型吃不准时不要瞎填一个——填错会让执行方从错误的阶段重新开始验证。
> - **完成标准**：目标项目、参考输入、受影响产物三者都已记录，且修订类型取自封闭枚举（四选一）。

**这四块只属于设计类**，因为设计修订的语义和代码交付完全不同：设计不是「提交一段 diff」，而是「在某个已有设计项目上，依据某些参考输入，改动某几份产物」。所以它要收集的是——改哪个项目、参考什么、会动到哪些产物、以及这是一次什么性质的修订。代码类那三块（交付方式/测试豁免/已验证事实）在这里一个都用不上，反过来这四块在代码类里也没有对应物。

其中**修订类型是活字段**（需求更新 / 视觉刷新 / 流程变更 / 范围新增），这也是它必须取自封闭枚举的原因：执行方是拿这个值去决定「从哪个设计阶段往后重新验证」的。

最容易错的地方：**修订类型填错范围**。把一次「流程变更」误填成「视觉刷新」，执行方就会只从靠后的视觉阶段重验，跳过了实际被改动的流程阶段——重验了错误的范围，看起来跑完了，实则漏验。这个字段填错的代价不是当场报错，而是下游安安静静地验错了地方，所以吃不准时宁可不填也别瞎填。
